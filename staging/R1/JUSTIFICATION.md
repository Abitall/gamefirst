# R1 — Justification

Every semantic unit of `artifact/library/core/rules/R1-build-is-truth.md`, why
it exists, what breaks if it is removed, and where the idea comes from.

| # | Unit | Why it exists | What breaks if removed | Source / inspiration |
|---|---|---|---|---|
| 1 | Rule sentence ("A claim of done is accepted only with an artifact…") | States the accept/reject test in one line, so a disagreement is about the artifact, not about tone. | The rule becomes advisory; "done" reverts to meaning "described". | Mindustry `CONTRIBUTING.md` ("Do not submit something without at least running the game"); Django contribution style |
| 2 | Why paragraph (87k words, zero build checks) | Names the concrete past failure that caused this rule, so it cannot be deleted later as redundant style advice. | The rule looks like generic good practice and is the first thing cut under time pressure. | Project history (v0.2); R6 reason for an addition to exist |
| 3 | "Store each artifact or its run log under `evidence/`; cite the path" | Turns evidence into a reviewable file instead of a memory of a terminal session. "Or its run log" covers a test that lives in `tests/`, whose artifact is the output, not the file. | Claims become unverifiable a week later; or tests are copied into `evidence/` to satisfy the letter of the rule. | Kubernetes `make verify` local-verification habit; CLI10 `capture` |
| 4 | Mechanic row: failing-then-passing test, or capture with steps | A game mechanic can pass a unit test and still be unplayable; two artifact kinds cover logic and feel. | Test-only evidence lets a broken mechanic ship; capture-only evidence lets regressions back in. | Django `submitting-patches.txt` (regression test requirement); SWE-bench FAIL_TO_PASS |
| 5 | UI row: screenshot or 10–30 s capture | UI fails visually, not logically; only a rendered frame proves layout, overlap, and readability. | "UI is done" is asserted from code structure that was never drawn. | Godot bug template (screenshot + text required, not either alone) |
| 6 | Content row: count from the running build + one opened sample | Separates "authoring data exists" from "content is in the game"; catches unreferenced or unregistered entries. | Content claims rest on data files nobody loaded; the game ships emptier than the spreadsheet. | raylib examples index (every example listed, compiled, runnable) |
| 7 | Performance row: trace + the budget it is compared to | A number without a target is not a result; a trace without a target cannot pass or fail. | Performance claims become "it feels fine", which is unarguable and unfalsifiable. | Bevy contribution flow (reviewers approve only after CI); general profiling practice |
| 8 | Release row: installed and launched from a clean OS profile, container, or machine; a second machine is not required | The only claim a player experiences directly; a dev-machine build hides missing files and dependencies. Naming the cheap clean environments keeps the bar affordable for one person. | Release readiness is inferred from a passing CI job that never installed the artifact, or the row is skipped as impossible without a second PC. | OSSF Scorecard `CI-Tests` (counts only tests that ran successfully) |
| 9 | "Weakened, skipped, or never executed is not evidence. Zero tests is not a pass." | Closes the cheapest way to satisfy every other row, which is to make the check trivial. | The rule is satisfied by deleting an assertion, and the metric improves while quality drops. | SWE-bench `SUITE_RAN` guard ("to tell 'ran with no failures' apart from 'never ran'") |
| 10 | Mode `discuss` | Discussion produces no artifact by nature; without this line the rule is violated on every conversation. | The agent either fakes evidence or refuses to think aloud. | Blueprint: mode > rules priority; mode list in `docs/V0.3-BLUEPRINT.md` |
| 11 | Mode `prototype`: the build may be discarded after it runs; capture and run log stay in `evidence/`; production gets no discount | Settles what survives a prototype — the evidence, not the code — and stops the discount from leaking upward. | Prototype artifacts vanish with the code, so a later "we proved X" claim has nothing behind it; or the exemption is stretched to production. | S08 `prototype` (disposable greybox still played); Godot MRP (the artifact outlives the session) |
| 12 | Mode `production` | Binds the rule to the existing gate (`verify`) and to an existing document field, so no new process is invented. | The rule floats free of the workflow and is remembered only when convenient. | `template/docs/systems/SYSTEM-CARD.md` (`verified by`); S02 `verify` |
| 13 | Mode `autonomous` | Removes the human who would otherwise ask "did you actually run it?"; the log entry becomes the reviewer. | Unattended runs produce confident reports with no checkable content. | X01 autonomy contract (`runs/AUTONOMY.jsonl`, checkpoints) |
| 14 | Mode `review` | Tells the critic what to grade: the artifact, not the write-up. | Review rewards good prose; the best writer wins, not the working build. | A04 `critic` (blind, read-only); OSSF Scorecard (evidence from CI, not from claims) |
| 15 | Not-evidence list | Enumerates the substitutes that actually get used; a principle alone does not stop them. | Each listed substitute is argued case by case as "basically evidence". | Bevy PR flow (CI + tests before approval); Godot MRP requirement |
| 16 | "When it cannot run" paragraph | Gives the agent a legal way to fail, which is what makes honesty cheaper than invention. | The rule creates pressure to fabricate an artifact rather than report a blocker. | E08 `stop after three`; Godot MRP ("a prerequisite for contributors to be able to solve them") |
| 17 | Check line: `verify` is the default; an exception comes from the user or the partner agent, never self-granted, with a reason and a date | Makes the rule executable by existing tooling, makes every exception visible and datable, and fixes who may sign one. | The agent grants itself an exception whenever the build is inconvenient; "default" becomes optional and the rule erodes silently. | CLI03 `verify`; Kubernetes required CI checks; X01 autonomy contract (authority is stated, not assumed) |
| 18 | Boundary sentence (R5, E03) | Prevents three parts from restating one idea in three places, which is the failure mode this framework exists to avoid. | Duplication and drift: two rules disagree, and the agent follows whichever it read last. | Blueprint "one fact in one place"; rubric §1 (duplication) |

## Deliberate omissions

| Omitted | Reason |
|---|---|
| A definition of "runnable" per engine | Engine packs own their run command; core must not name one (blueprint: no engine imports in core). |
| A fun/quality judgement | R8 owns it; R1 only asks whether the loop was played, not whether it was good. |
| A reward or scoring scheme | E03 and the gates already score compliance; a second score would duplicate. |
| A list of accepted test frameworks | Same reason as engines: it would pin the core to a toolchain. |
| Examples of good evidence | Would double the token size and rot; the table's artifact column is the example. |
