# G2.5 - feature freeze

Not a gate. After G2 says `proceed` and before content starts, the human signs one dated record of what is frozen; the agent brings the list, never the signature.

## Record

Append one dated decision to `DECISIONS.md`; `STATE.md` points at it. Four parts:

- **Date** - the day the list is signed; S11 and S12 read it.
- **In** - every mechanic, system, mode and screen the build ships, by name and entry point. A feature not on the list is not in the game.
- **Out** - the ordered cut list from G2, each line with its cost and what the build loses.
- **Budget** - the G2 content numbers, by reference to the G2 packet; do not restate them.

## After the freeze

Only fixes. A change is a fix when it restores behavior the frozen list already promised; it is a feature when it adds a mechanic, system, mode, screen, input or content type. Renaming, moving or re-tuning a value is a fix. R9 prices everything else.

- **One in, one out** - a feature added now removes a feature of comparable cost, named in the same decision (R9).
- **A bug found** - triage in one line: severity, steps, regression or known. Blockers and regressions are fixed with a test; the rest goes to `BACKLOG.md`. A fix that needs a system change is a feature.
- **Disable beats late** - a frozen feature that misbehaves near release is disabled, not repaired in place.

## Boundary

S11 fills the budget, then S12 polishes; the freeze holds until G3, and no dated line means no S11. G3 decides ship or hold. G2.5 does not re-check the nine G2 points S10 evidenced, add a tenth, reopen the slice, or move a number G2 wrote. An idea goes to `BACKLOG.md` with its cost (R9, E06): the freeze does not reject it, it prices it.
